# Remote workspace security audit — 2026-10-26

## Native host mode extension

Native Linux workspaces deliberately use the SSH account's ordinary host
permissions. Full root makes its existing unrestricted passwordless sudo
available to agents, with nonprompting harness defaults; Normal user enables
no-new-privileges for direct launches. Neither mode claims isolation against
the same account or a host administrator. The user service and Chromium stay
non-root. The permission warning is required on creation and retained in
settings. Access mode is fixed for each installed workspace.

The host installer verifies the source manifest/fingerprint before extraction,
checks pinned Node archive SHA-256 values, installs the locked target-native npm
graph, and activates runtime links with health and browser checks. Failed
activation restores the environment, unit, record and previous links. Shell
startup files and existing harness configuration are audited around installers;
pre-existing CLI installations are never treated as Woven-owned updates.
Host environment parsing does not evaluate shell text. Administrative credentials
stay in stdin and a 0600 environment file, and managed directories are private.
Every Mac SSH path retains Tailnet peer verification and strict host keys.

Native Chromium explicitly enables its sandbox. Its self-test correlates CDP
process IDs with renderer ancestry, separate user/PID namespaces, seccomp and
no-new-privileges evidence; unknown evidence fails closed. Profiles separate
website state and reject unsafe IDs/symlink paths. The service does not supply
its API credential to the browser. CDP and the control listener remain loopback.

Existing container hardening and browser launch behavior are retained during
native evaluation. Enabling the inner Chromium sandbox in those containers
remains separate work requiring a verified seccomp/AppArmor combination; this
change does not weaken capabilities, filesystem protection or namespace policy.
Host mode has no Docker dependency or unsandboxed fallback. See
[Native Linux hosts](REMOTE_HOSTS.md) for the complete operating model.

## Scope and trust model

Reviewed the desktop connection, SSH provisioning/lifecycle, attachment and shared
file transfer, Docker image/Compose definitions, control HTTP service, scoped
execution grants, runtime installers, instance proxies, persistent storage,
scheduling, client publication paths, and the separate managed Executor image
and deployment flow. Host-wide services are outside the image boundary. No
installed workspace, Executor, Docker daemon, or Tailscale daemon was changed.

The external network boundary is Tailscale. Peer selection comes from the local
trusted daemon, and SSH streams use that daemon's `DialTCP` transport through
`tailscale nc`. The workspace API additionally requires its administrative bearer
credential or a scoped device credential; Tailscale access does not remove API
authorization. HTTPS sharing requires private Serve and rejects Funnel exposure.
Root/Docker administrators and the SSH account are trusted. Agents sharing a
workspace also share a UID, persistent home, provider access, and outbound
network. This is not a sandbox between agents or a defense against host root.

## Findings addressed

| Finding | Change |
| --- | --- |
| Arbitrary SSH hosts and SSH proxy configuration could select a LAN/public path. | Every production workspace and Executor-deployment SSH entry point independently resolves one verified online Tailnet peer and forces `tailscale nc`. Removed optional-Tailscale setup language and generic host guidance. No LAN mode or compatibility path remains. |
| A multiplexed SSH connection or a tunnel cached only by configuration ID could survive a destination change. | Disable SSH multiplexing and reuse a tunnel only when the full configuration and freshly resolved peer transport options still agree. |
| Older Docker localhost publications can be reachable from adjacent hosts. | Reject Docker Engine versions below 28 in inspection and lifecycle operations. |
| Workspaces shared Docker's default bridge. | Dedicated owned NAT bridges, inter-container communication disabled, no trusted external interfaces, and loopback-only publication. Start/share checks reject containers that have not been updated. |
| The standalone Executor used Docker host networking. | It now uses its own managed bridge with inter-container communication disabled and publishes only to `127.0.0.1`. Tailscale Serve is the sole remote route. A failed upgrade never restores a legacy host-network container. |
| Lifecycle could operate on an unrelated container with the expected name. | Require matching workspace ownership labels before reading status or changing/deleting/sharing a container; retain volume ownership validation. |
| API tokens appeared in `docker`/`sudo` process arguments. | Use a private, automatically cleaned environment file; validate credential length and characters before activation. The image health check also reads its credential inside Node rather than putting it in curl arguments. Docker administrators can still inspect container environment, as expected under the host trust model. |
| Root-owned lifecycle locks could follow a precreated symlink. | Require an owned ordinary lock directory before setting permissions or acquiring locks. |
| Process creation and newly created file permissions were insufficiently constrained. | Limit containers to 512 processes, disable core dumps, set service umask 077, and use nodev temporary mounts. |
| Administration requests could follow redirects away from their tunnel. | Restrict the native service client to its loopback origin, disable system proxies and cookies, and refuse redirects per task. |
| Deployment contexts and app resources could retain local install caches or environment files. | Restrict Docker context inputs, exclude node_modules and environment files from SSH deployment archives, and trim these from bundled remote resources. |
| HTTP parsing and error responses offered unnecessary attack surface. | Bound headers/upload deadlines/connections, reject browser-origin and absolute-form targets, use a fixed parsing origin, and mask unexpected internal error details. |

## Existing controls reviewed

Administrative and device grants remain separate. Device scopes do not convey
runtime installation, credentials, sign-in, or workspace administration. Grants
use random bearer secrets and hashed token lookup; revocation is persisted.
Unlock envelopes and publisher credentials use authenticated encryption bound to
the workspace/device identity. The outbound publisher refuses redirects.

Container processes retain non-root identities, dropped capabilities,
`no-new-privileges`, read-only image layers, private home volumes, bounded rotated
logs, and image replacement with rollback. The standalone Executor has the same
read-only root, capability, privilege, PID, loopback-publish, and private-bridge
controls; its persistent data bind mount is the only writable state. File retention opens bounded regular
files without following final symlinks and checks the opened descriptor's
confinement and identity. Managed databases and project operations restrict their
paths. Instance proxies validate loopback registrations and reject redirects.
Installers require HTTPS and bounded downloads; reviewed script digests must match
at execution. npm packages retain registry integrity verification. Tests use
provider-free fixtures; no live sign-in or provider request is part of this review.
